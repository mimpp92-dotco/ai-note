# Plan 스킬 보강안

## 배경

이번 세션에서 `plan` 스킬을 사용해 기존 `docs/plans/sidebar-polish-glossary-menu-fixes/` 문서를 검증하고 보강했다. 스킬의 핵심 의도인 정본 문서 기반 검증, 실제 코드 대조, 누락 보강은 잘 작동했다.

다만 요청이 "새 기획 생성"이 아니라 "이미 존재하는 plan 검증/보강"일 때, 현재 스킬 흐름은 약간 과하다. 새 plan 초안 생성, 승인 후 폴더 생성, phase 문서 생성 중심으로 설계되어 있어 기존 plan 감사를 위한 얇은 경로가 있으면 더 효율적이다.

## 목표

기존 `plan` 스킬에 큰 모드나 복잡한 절차를 추가하지 않고, 기존 plan 검증/보강 요청을 자연스럽게 처리하는 최소 규칙을 추가한다.

원칙:

- 새 plan 생성 흐름을 복잡하게 만들지 않는다.
- 기존 7관점 검증 철학은 유지한다.
- 작은 요청에 감사 보고서 같은 과한 산출물을 강제하지 않는다.
- 사용자가 명시적으로 반영을 요청한 경우에만 기존 plan 문서를 수정한다.

## 제안 변경

`plan` 스킬의 `0. 입력·스코프 게이트` 근처에 아래 짧은 절을 추가한다.

```md
### 기존 plan 검증/보강 요청

사용자가 기존 `docs/plans/<slug>/`의 검증·보강을 요청하면, 새 plan 생성 흐름을 시작하지 않는다. 해당 plan을 초안으로 간주하고 정본 문서·ADR·실제 코드와 대조해 누락/충돌/불명확한 구현 결정을 찾는다.

검증 결과가 여러 항목이면 `앵커 / 문제 / 보강안 / 근거` 중심으로 짧게 보고한다. 사소한 요청은 prose로 답한다.

사용자가 “반영/보강/수정”을 명시하면 기존 plan 문서 수정 승인으로 본다. 단, phase 추가·삭제나 scope 확대는 별도 확인하며, 앱 코드 수정은 하지 않는다.
```

## 왜 이 정도가 적절한가

### 1. 기존 plan 검증 경로는 필요하다

현재 스킬은 새 기획 생성에 최적화되어 있다. 하지만 실제 사용에서는 이미 만들어진 plan을 다시 검토하거나 보강하는 요청이 자주 생긴다.

이때 새 plan 생성 루프를 다시 시작하면 불필요하게 무거워진다. 기존 plan을 "초안"으로 간주하고 정본 문서/코드와 대조하는 얇은 경로만 있으면 충분하다.

### 2. 별도 대형 모드는 과하다

`기존 plan 검증 모드`를 큰 절차로 만들면 오히려 스킬이 복잡해진다. 에이전트가 모드 선택부터 고민하게 되고, 작은 검토 요청에도 과한 절차가 실행될 수 있다.

따라서 별도 모드 대신 입력 게이트의 예외 경로로만 둔다.

### 3. finding 형식은 강제가 아니라 압축 규칙이면 충분하다

`severity / anchor / evidence / issue / fix` 같은 엄격한 템플릿을 항상 강제하면 기획 스킬이 코드리뷰 도구처럼 무거워진다.

대신 항목이 여러 개일 때만 `앵커 / 문제 / 보강안 / 근거` 중심으로 압축하면 된다. 사소한 검토는 자연어 답변으로 끝낼 수 있어야 한다.

### 4. 승인 규칙은 좁게 필요하다

스킬에는 "승인 전 `docs/plans/`에 아무것도 쓰지 않는다"는 강한 규칙이 있다. 기존 plan 보강도 `docs/plans/`를 수정하는 일이므로, 검증과 수정의 경계를 분명히 해야 한다.

다만 승인 규칙이 넓으면 위험하다. 사용자가 단순히 의견을 물었는데 문서가 수정될 수 있기 때문이다. 그래서 "반영/보강/수정"처럼 명시적인 요청이 있을 때만 기존 plan 문서 수정 승인으로 본다.

## 기대 효과

- 기존 plan 검증 요청에서 새 plan 생성 절차를 반복하지 않는다.
- 정본 문서와 실제 코드 대조라는 스킬의 장점은 유지된다.
- 사용자에게는 바로 실행 가능한 보강점이 짧게 제공된다.
- 승인 전 파일 수정 금지 원칙과 기존 plan 보강 작업이 충돌하지 않는다.
- 스킬 본문 증가량이 작아 context 비용이 낮다.

## 의도적으로 하지 않는 것

- 별도 `existing-plan-audit` 모드 신설.
- finding 보고서 템플릿 강제.
- 모든 기존 plan 검토에 7관점 전체 보고 강제.
- 사용자 승인 없이 `docs/plans/` 수정.
- 기존 plan 검증용 별도 스크립트/리소스 추가.

## 적용 위치

권장 위치는 `SKILL.md`의 `0. 입력·스코프 게이트` 섹션이다.

이유:

- 기존 plan 검증 여부는 작업 초기에 판별해야 한다.
- 새 plan 생성 흐름으로 들어가기 전에 분기해야 한다.
- 정본 문서/코드 탐색 규칙과 가장 가까운 위치다.

## 수용 기준

- 기존 plan 검증 요청 시 새 plan 폴더를 만들지 않는다.
- 기존 plan 문서를 초안으로 삼아 정본 문서와 실제 코드에 대조한다.
- 보강점이 여러 개면 `앵커 / 문제 / 보강안 / 근거` 중심으로 보고한다.
- 사용자가 명시적으로 반영/보강/수정을 요청하기 전에는 `docs/plans/`를 수정하지 않는다.
- phase 추가/삭제 또는 scope 확대가 필요하면 별도 확인한다.
- 앱 코드나 설정 파일은 수정하지 않는다.
